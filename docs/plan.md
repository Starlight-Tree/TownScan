# 計画（spec-driven）

状態: **方向は承認済み**（2026-11-24。[ADR 0002](decisions/0002-direction.md)）。**対象は 2026-11-27 に熊本からフランスへ変えた**（[ADR 0015](decisions/0015-move-to-france.md)。方向・指標の定義・出口条件とも承認済み。移行の段は §4.1）。熊本の時期の計画の本文は、Git の履歴（`a72748e` の `docs/plan.md`）にある。

## 1. 何を作るか

パリ南西の近郊（県 92 の 12 地区）で、**空中写真（IGN。2014 年と 2024 年）から新築の候補を棟ごとに検出**し、会話で聞けるアプリ。回答は短い本文と表示 1 つで返す（[ADR 0013](decisions/0013-one-view-per-answer.md)）。範囲外の質問は断る。

- **屋根の太陽光パネルを数える機能は、後のフェーズで追加し、新築の候補と合わせたハイブリッドにする**（ユーザー決定 2026-11-27。時期と範囲は未定）。
- 衛星（Google Earth Engine）で広域の変化の当たりをつける層は後の拡張で、やるかは未決。「面で当たりをつけ、棟で確かめる」二段構えで、GEE の結果は「変化の当たり」と呼び、「新築」とは言わない。
- 棟の結果は「**候補**」と呼ぶ（「新築」と断定しない。[ADR 0010](decisions/0010-candidate-wording-and-count-card.md)）。分類の呼び名は、モデルが確認した事実にする（[ADR 0011](decisions/0011-class-labels-by-observation.md)）。画面の分類は「2014 年は未検出」「未判定」の 2 つ（[仕様 §5](spec-prototype.md)）。**差分は入口で、確定は写真**。

完了の目安（スクールの課題としての「完成」。ユーザーが決める）:

- 質問に、ツールの結果（件数・表・地図・写真）を根拠として答える。数字は結果の値だけから出し（返答文の数字は結果と照合して検査する。[ADR 0009](decisions/0009-llm-writes-result-numbers.md)）、表示はツールの結果をそのまま描く。
- 画像認識の評価が、再現できる手順と数字で残る（指標の定義は [ADR 0015](decisions/0015-move-to-france.md)）。
- 公開した説明（README・スクリーンショット・限界の明記）がある。

## 3. 進め方（AI 駆動開発）

> 出どころ: spec-driven development は解説記事ベース（検索結果の要約。原文は未精読）。Claude Code の使い方は公式の [Best practices](https://code.claude.com/docs/en/best-practices) を検索で確認（本文は未精読）。一般知識を含む。

1. **仕様が正本、コードは派生。** 各段の始めに、この文書へ「完了条件（実行できる検査）」を書いてから実装する。
2. **評価を先に作る（evals-first）。** 正解データ・指標・ベースラインを先に作り、以降は指標を落とさない。
3. **段ごとに「計画 → 実装 → 検証」。** 計画は plan mode（読み取りだけ）で立て、承認してから実装する。
4. **検証できない変更は出さない。** `scripts/verify.sh` が合格してから報告する。強制したいことは、文章ではなく権限・フックにする。
5. **決定は ADR（[`docs/decisions/`](decisions/README.md)）に 1 件 1 ファイル。** データのライセンスのように、後で効くものは、公式の URL で確かめたものだけを書く。
6. **実装と別の目で見る。** 段の終わりに、読み取り専用のレビュー（`/code-review`）。指摘は読んで確かめてから採る。
7. 実 API（課金）・外部への書き込み・新しいサービスは、件数・回数・概算費用を示して承認を得てから。

## 5. 設計の骨子

- スタックは、ユーザーの既存の型に合わせる: Next.js（Node 24）、Postgres 17、解析は Python 3.13。**API は Go**（ADR 0005）。**PostGIS など新しい DB 拡張・サービスは、ADR で承認を得る**（今は拡張なし）。
- チャットは、ツール呼び出しの結果を**判別可能ユニオン型＋固定部品**で描く（ShopOrder と同じ方針）。数字・件数・座標は、ツールの結果の値だけから出る（LLM の説明文に書かれる数字は結果と照合して検査し、座標・ID は書かせない。ADR 0009）。
- 「根拠付き」は、ツール結果に出どころ（データ名・撮影年・指標）を必ず持たせて表す。
- LLM は、開発・実行の既定が実 Gemini（ユーザー決定 2026-11-25。[ADR 0003](decisions/0003-llm-provider.md)）。模擬モデルは、契約の検査・テストと、Claude Code の内部の検証のときだけ環境変数で選ぶ。
- 建物の抽出の推論は Google Colab（T4）で必要なときに流し、後処理・読み込みは手元で行う。学習はしていない。
- **GEE 層の条件**（ADR 0002）: ①「新築」と言わず「変化の当たり」と呼ぶ。②写真が無い期間は UI で「棟の確認は不可」と明示する。③公開デモは、GEE の結果を事前計算して静的に配信する（非商用の枠を、見に来た人で共有しないため）。④チャットの完成後に回す。

## 6. リスク・未確認

- **アプリの写真（IGN の配信タイル）での精度は測っていない。** 比較の値は FOTBCD の val で、調整に使ったデータの値（ADR 0016「限界」）。
- **評価用の FOTBCD は人が選んだ標本**で、断片はばらばら。同じ場所は 2 時点だけ（ADR 0015）。
- **公開（P7）の前に確認:** IGN の配信タイルと BD ORTHO の利用条件（Licence Ouverte 2.0。出典の表示）、モデルとデータの出典の表示、公開先と費用。写真を機械学習に使うことは、利用規約に記載が無い（仕様 §7 の `/accuracy`）。
- **GEE（調査日 2026-11-24。公式ページの検索で確認）:** 非商用の枠は月次の計算量（Community 150 EECU 時間）で、商用に切り替えると引き継がれない。Detect change は Google Earth の機能で、アプリから API で呼べるかは未確認（使うなら、Earth Engine で埋め込みの差を自前で計算する）。10 m では新築 1 棟は 1 ピクセル前後で、棟の確認には使えない。埋め込みは土壌水分のように写真に写らない変化も拾う。
- データのライセンス: パネルのデータは P6 の前に確認する（候補は ADR 0001）。IEEE BigData Cup 2024 は Non-Commercial and Academic Research Only（参考にするだけで、データは使っていない）。
- GPU が無い（Mac の Docker）。推論は Colab。
