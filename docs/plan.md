# 計画（spec-driven。2026-11-24 に方向 B 案で書き換え）

状態: **方向は承認済み**（2026-11-24。[ADR 0002](decisions/0002-direction.md)）。承認待ちは末尾の 5 つ。数字（時間）は推定で、実測ではない。P2 の小実験のあとに取り直す。

## 1. 何を作るか

熊本市の中心部で、**空中写真から新築の候補を棟ごとに検出**し、**衛星（Google Earth Engine）で広域の変化の当たりをつけ**、会話で聞けるアプリ。答えは集計・地図・表・検出画像で、**根拠付き**で返す。範囲外の質問は断る。屋根の太陽光パネルは後半の拡張。

- 「面で当たりをつけ、棟で確かめる」二段構え。GEE の結果は「変化の当たり」と呼び、「新築」とは言わない。
- 棟の結果は「**新規出現候補**」と呼ぶ。3 分類にする: `confirmed_new`（旧写真に無く新写真にある）／`existing_omission`（旧写真に既にある。建物データの描き漏れ）／`uncertain`。**差分は入口で、確定は写真**。

完了の目安（スクールの課題としての「完成」。ユーザーが決める）:
- 質問に、ツールの結果（件数・表・地図・検出画像）を根拠として添えて答える。数字は LLM に書かせず、ツールの結果をそのまま描く。
- 画像認識の評価が、再現できる手順と数字で残る（建物は IEEE BigData Cup 2024 の物体単位 F1 を参考にした指標。新築の再現率は手ラベル）。
- 公開した説明（README・スクリーンショット・限界の明記）がある。

## 3. 進め方（AI 駆動開発）

> 出どころ: spec-driven development は解説記事ベース（検索結果の要約。原文は未精読）。Claude Code の使い方は公式の [Best practices](https://code.claude.com/docs/en/best-practices) を検索で確認（本文は未精読）。一般知識を含む。

1. **仕様が正本、コードは派生。** 各段の始めに、この文書へ「完了条件（実行できる検査）」を書いてから実装する。
2. **評価を先に作る（evals-first）。** P2 で正解データ・指標・ベースラインを作り、P3 以降は指標を落とさない。
3. **段ごとに「計画 → 実装 → 検証」。** 計画は plan mode（読み取りだけ）で立て、承認してから実装する。
4. **検証できない変更は出さない。** `scripts/verify.sh` が合格してから報告する。強制したいことは、文章ではなく権限・フックにする。
5. **決定は ADR（`docs/decisions/`）に 1 件 1 ファイル。** データのライセンスのように、後で効くものは、公式の URL で確かめたものだけを書く。
6. **実装と別の目で見る。** 段の終わりに、読み取り専用のレビュー（`/code-review`）。指摘は読んで確かめてから採る。
7. 実 API（課金）・外部への書き込み・新しいサービスは、件数・回数・概算費用を示して承認を得てから。

## 5. 設計の骨子（P3・P4 で ADR にする）

- スタックは、ユーザーの既存の型に合わせる: Next.js（Node 24）、Postgres 17、解析は Python 3.13。**API は Go**（ADR 0005。それまでの FastAPI は、置き換えて消す）。**PostGIS など新しい DB 拡張・サービスは、ADR で承認を得る。**
- チャットは、ツール呼び出しの結果を**判別可能ユニオン型＋固定部品**で描く（ShopOrder と同じ方針）。数字・件数・座標は LLM に書かせない。LLM は「どのツールを呼ぶか」と、結果の説明だけ。
- 「根拠付き」は、ツール結果に出どころ（データ名・撮影年・指標）を必ず持たせて表す。
- LLM は模擬モデルが既定。実モデルへの切り替えは、承認を得てから環境変数で選ぶ。
- **GEE 層の条件**（ADR 0002）: ①「新築」と言わず「変化の当たり」と呼ぶ。②写真が無い期間（2024〜2025 年）は UI で「棟の確認は不可」と明示する。③公開デモは、GEE の結果を事前計算して静的に配信する（非商用の枠を、見に来た人で共有しないため）。④チャットの完成後に回す。⑤比較できる年は 2017〜2025（2008・2016 年の写真は対象外）。
- 計算はコンテナ（RAM 約 7 GB・GPU なし）では推論だけ。学習は Kaggle / Colab。

## 6. リスク・未確認

- **地理院タイルの機械学習・大量取得の扱いは未確認。** 規約ページに制限の記載は見つからなかった。問い合わせは未実施（外部送信なので、文面を見せてから）。

- **建物データ（基盤地図情報）は 2017-10 で凍結。** 2018 年以降の新築は載らない。評価の参照は写真と同時期の版に揃え、新築の再現率は手ラベルでしか測れない（P1 の発見。ADR 0001）。
- **写真の年:** 熊本中心部は 2008・2016・2023 年が揃う（2023 年は 2018 年の範囲をすべて含む）。**2018 年は斜めの帯状の断片（簡易空中写真 2018 年 12 月）で、z18 で写真があるのは対象の約半分（約 17 km²。ADR 0001 の訂正）。2018 vs 2023 の同解像度の差分は、この帯の中に限る。** 2024・2025 年の年度別タイルは、対象内では北端の細い帯のみ（未確認の部分あり）。郊外は 2023 年が無い。
- **GEE（調査日 2026-11-24。公式ページの検索で確認）:** 非商用の枠は月次の計算量（Community 150 EECU 時間）で、商用に切り替えると引き継がれない。Detect change は Google Earth の機能で、アプリから API で呼べるかは未確認（使うなら、Earth Engine で埋め込みの差を自前で計算する）。10 m では新築 1 棟は 1 ピクセル前後で、棟の確認には使えない。GEE の埋め込みは土壌水分のように写真に写らない変化も拾う。
- **事前学習の建物抽出モデル**（凍結した基盤モデルの encoder に軽い検出部を足す構成が、2026 年の論文に出ている。熊本の写真での精度は未確認）の、ライセンスと精度は、P2 の前に確認する。
- データのライセンス: IEEE BigData Cup 2024 は Non-Commercial and Academic Research Only（再配布は避ける）。パネルのデータは P6 の前に確認（候補は ADR 0001）。
- GPU が無い（Mac の Docker）。学習は Kaggle / Colab、アプリは推論だけ。
