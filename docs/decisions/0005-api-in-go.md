# 0005 API は Go、解析は Python（契約を先に決め、Python の API を置き換えて消す）

状態: **承認済み**（ユーザー、2026-11-25「Go でやれ」「このプロジェクトに限らず、今後全て API は Go にする」）。**実装はこれから。この文書の時点では、Go のコードは無い。**

## 決めたこと

- **HTTP の API（`/api/*` のすべて）を Go で作る**: 地区・候補・GeoJSON・候補の詳細・検出画像の切り出し・メトリクス・ヘルス・`/api/me`（JWT の検証）・**チャット**（ツール・数字の検査 `guard_numbers`・模擬モデル・Gemini の窓口）。
- **Python は解析だけを担う**: `pipeline/`（建物の抽出の後処理・差分・3 分類・評価）と、その出力を DB へ読み込む処理（`app.load`）。GEE の事前計算（拡張 1）も Python（Earth Engine の公式クライアントは Python と JavaScript）。画像認識・LLM の学習側の依存は、Python に閉じる。
- **置き換えて消す。二重にしない**: Go の API が契約を満たしたら、Python の API（`backend/app` の API 部分）は消す。切り替え中の短い期間だけ、同じ契約の検査を両方に流す。
- **契約を先に決める**: 言語に依らない「契約の検査」（HTTP で叩く pytest。`contract/`）を先に作り、いまの Python の API で通ることを確かめる。Go の API は、これを満たす。frontend は変えない（契約が同じなので）。
- **配置**: Go の API は `api/`（モジュール `townscan/api`、`cmd/api/main.go`、`internal/…`）。`backend/` は、Python の API を消したあと、解析側の読み込みだけが残る（その時点で `pipeline/` へ移す）。
- **流儀は DocuNavi の Go にそろえる**（逐語の同一。`cmp` で確かめる）: Go 1.26.x（`go.mod`・`.go-version`）、標準ライブラリを先に使う、静的ビルド（`CGO_ENABLED=0 -trimpath`）＋ distroless、`go vet`・`go test -race -count=1`、開発コンテナへは `install-go.sh`。
- **依存は最小**: 標準ライブラリに加え、Postgres のドライバー（`pgx`）、JWT の検証、画像の縮小（`golang.org/x/image`）の見込み。**入れる前に、版・用途・代わりの案を示して承認を得る**（標準だけで足りるものは入れない）。

## 理由（背景）

- ユーザーの決定: 拡大するサービスにも耐える汎用的な設計を最初から採り、構成を何度も変えない。Go のバックエンド経験も学ぶ。速さを優先する。今後作る API はすべて Go にする、という方針も、ユーザーが同日に決めた（TownScan はその最初の適用）。
- **責任の境界が明確**: 画像認識・LLM に近い解析は Python のエコシステム、ネットワークと並行処理の層は Go。TownScan はすでに「オフラインの解析 → DB → API」で、境界が DB にある（`python -m app.load`）ので、API だけを置き換えられる。
- **この決定は、いまの速さの不満によるものではない。** 2026-11-25 の実測（ローカル、実データ 18 候補、各 30 回の中央値）では、Python の API は一覧・集計・詳細・チャット（模擬）で 1 ms 前後、画像の切り出しで 17〜19 ms だった。言語が律速にはなっていない。Gemini の応答待ち（平均約 6 秒）は言語に依らない。**Go にしても、いまの体感は変わらない。** 拡大したときの余裕と、設計の一貫性が目的。
- 「最新トレンドだから」は理由にしない。調査（出どころつき）の結果は、別に残す（調査は 2026-11-25 に実施。この文書の時点では未反映）。

## 結果（予定する順序）

1. **契約**: `docs/spec-prototype.md` の API の節と、`contract/`（HTTP の検査。いまの Python で通す）。出口条件: Python の API に対して全件合格。
2. **Go の土台と読み取り API**: 設定・エラー形式・DB・ヘルス・地区・候補・GeoJSON・詳細・メトリクス。出口条件: 契約のうち該当部分が Go で合格。
3. **認証**: JWT・JWKS の検証・`/api/me`。出口条件: 契約と、`jwt_tokens` の同等のテストが合格。
4. **検出画像**: タイルの切り出し・縮小・出どころの表示。出口条件: 契約と、画像の検査（大きさ・形式・範囲外の拒否）が合格。
5. **チャット**: ツール・`guard_numbers`・模擬モデル・Gemini（再試行・27 秒の期限・502）。出口条件: 契約のチャットの全件が合格（数字は結果の値と一致する）。
6. **切り替え**: `compose.yaml` の api を Go のイメージに替え、Python の API を消す。出口条件: `scripts/verify.sh`（`go` を含む全段）と実機の `scripts/dev-up.sh` で、画面の操作が従来どおり。
7. **その後**: チャットのストリーミング（DocuNavi の Go の SSE 中継を写す）、検出画像のキャッシュ、DB の索引とページ分け（PostGIS・索引の追加は別に承認）。

## 選ばなかった案

- **Python の API のまま**: 速さの実測は足りているが、ユーザーの決定（汎用的な設計・学習）に合わない。
- **Go を周辺（SSE 中継だけ）に限る**: 二言語の API が残り、責任の境界が曖昧になる。
- **Go の API と Python の API を並べて持つ**: 二重実装になる。切り替えのあいだの検証だけに限る。
