## 理由

**土台（DocuNavi の実物）。** 値（上限・件数・日数）は、DocuNavi のコードから取ったものだけを「DocuNavi の値」と書いた（DocuNavi main=a62c9aa。読み取りと `git grep` だけ）。DocuNavi の文書（`docs/api.md`）とコードが食い違うところは、コードを基準にした。

**D1（サーバーが回答と一緒に保存）:** 保存する回答の `results` を、**サーバーが作った値だけ**にできる（CLAUDE.md「数字・件数・座標は LLM に書かせない。ツールの結果をそのまま描く」を、開き直した画面でも守る）。回答と保存が 1 回の呼び出しで、回答は出たのに履歴に無い食い違いが作られない。保存するかを `conversation_id` の有無で決めるのは、サーバーが「無ければ作って返す」（DocuNavi の方式）にすると、ログイン中の要求の既定が変わり、「`Authorization` を見ない」既存の契約と衝突するため。画面が、ログイン中の新しい会話の最初の送信で `crypto.randomUUID()` を作る。他人の ID を知っても何もできない（主キーが `(user_id, id)`）ので、画面が決めてよい。文脈を保存した発言から組み直さないのは、未ログイン（`messages` から作る）とログイン中（保存から作る）で、文脈の作り方が 2 つになるのを避けるため。

**D2（表 2 つ）:** 上の対応表のとおり。TownScan のチャットは無状態で LangGraph を使わず、回答の本体は `results`（件数・表・地図・写真）。

**D3（API 3 本）:** DocuNavi の `GET /threads`・`GET /threads/{id}/messages`・`DELETE /threads/{id}` に対応する（`/api/conversations`）。`no-store` は、人ごとに違う内容のため付ける（DocuNavi の `app/api/threads.py` は付けていない。TownScan は付ける）。

**D4（JWT の渡し方）:** TownScan のブラウザーは、同じオリジンの `/api/*` を呼び、`frontend/proxy.ts` が API へ転送する。履歴の API は `Authorization: Bearer` が要り、いま画面は API へ JWT を渡していない。DocuNavi と同じに、ブラウザーが `GET /api/auth/token` で取る。新しい依存も経路の追加も無い。

**D5（画面）:** 1023px 以下は、サイドパネルを重ねて開く作り（上の横帯は 2026-11-25 にやめた）で、DocuNavi の狭い画面の一覧は「崩れないことの確認だけで、モバイル向けの最適化はしない」（CSS のコメント）。TownScan は、初版は作らない（保存は続く。あとで足せる）。

**D6（拡大ビューの状態を保存しない・run の食い違い）:** 回答の `results` は、その時点の run（`kind` が `synthetic` か `real` かも含む）の値で、候補 ID（`c-x-y-n`）・地区の `filter` も run ごとに違う。解析結果は、読み込み直すと入れ替わる（`python -m app.load`。表示するのは最新の run）。合成データで話した会話を、実データになってから開くと、カードの件数と地図が食い違う。DocuNavi の `scope_unavailable`（保存した検索範囲がいま見えない）と同じ種類の問題で、DocuNavi は「範囲を主張しない・続きは保存された範囲で探す」とする。TownScan は、「古い run の画面を作らない」とする。`run_id` だけでは、同じ `run_id` を後処理し直して読み込み直したときに見分けられないので、`run_created_at` も見る（J4）。

**D7（保存期間と件数）:** 一覧は新しい 50 件だけで、51 件目以降は画面に出ない。本人は、画面から ID を得る手段が無く、それらを消せない。掃除は手で流すので、「本人が消せる」「保存期間 7 日」だけでは保証にならない。保存を 50 件に収めれば、一覧に出る会話が保存の全部で、本人が消せる範囲と一致する。**保証できるのは、件数（50 件）のほう。** 7 日は目安（DocuNavi は Cloud Scheduler＋Cloud Run Job だが、TownScan はローカルだけで、定期実行の仕組みが無い）。

**D8（Go にだけ入れる）:** Python の API に入れると、同じ業務ロジックが 2 つの言語に置かれ（CLAUDE.md・ADR 0005 が禁じる二重実装）、すぐ消す Python の API にも契約の検査を足すことになる。保守コマンドを Go にするのも同じ理由（履歴の表を読み書きするのは API の仕事で、表の定義・削除の規則を 2 つの言語に置かない）。

**D9（500 件）:** **根拠は、既存の `MAX_CHAT_MESSAGES`（1 要求の入力の上限）の流用で、保存の大きさ・読み出しの大きさからは導いていない。** DocuNavi には上限が無いが足す。TownScan は `results` を丸ごと持つ。1 回の `map_focus` だけで候補 ID を最大 5000 件（`MAX_FOCUS_IDS`）含みうる。ID 1 件を約 20 バイトと見積もると、1 回で約 100 KB、回答 250 件がすべてそうだと 1 会話で約 25 MB になりうる（実測ではなく見積もり）。実データは候補が少なく（ADR 0005 の実測は 18 候補）、この大きさにはならない見込み。バイト数や `results` の上限は、初版では足さない（実測のあとに決める）。

**D10（保存の失敗）:** 回答だけ見えて履歴に無い食い違いを作らない。TownScan の `POST /api/chat` は、もともと DB から結果を作るので、DB が使えなければ同じく 503 になる。コードの誤りを「使えない」と偽らないため、500 は分ける（J1）。保存を飛ばした会話で `conversation_id` を付け直すと、保存済みの会話に欠けた往復ができ、開き直すと画面で見た会話と食い違う。API の側で件数を比べる案は、画面の履歴が、失敗した発言・40 件の切り詰めで、保存済みの件数とずれるため採らない。

**D11（LLM の前の検査・保存の SQL）:** 拒否された要求で課金しない。保存が SQLSTATE 22021・22P05（NUL）で失敗して 500 になり、LLM の費用だけが掛かるのを避ける。「無ければ作る（`DO NOTHING`）→ 別の文でロック」にしないのは、その間に別の `DELETE` が入ると、次の発言の挿入が `conversation_messages_conversation_fk` の外部キー違反（同じ SQLSTATE 23503）になり、「利用者の行が無い」と取り違えて 401 にしてしまうため。

**D12（文言）:** 文言はユーザーが案のとおりに決定した。

## 起草後の画面の変更に合わせた調整（前提の更新。要確認）

下書き v2（TownScan main=74fc640 を調べた）は、`/` の右に**常設の結果領域**がある画面を前提に、開き直しの「結果領域の静かな復元」を定めていた。その後、`/` の画面は**チャットだけの 1 列と拡大ビュー**に変わった（spec-prototype 改訂（8）。コミット 4384b5a。この文書の起点は 2311834）。常設の結果領域は無く、回答が届いても拡大ビューは開かず・画面は替わらない。回答ごとの状態は、カードのボタンを押して**はじめて開くとき**に、回答の結果から決める。

このため、spec-prototype §7.1.5 は、下書き v2 の規則のうち、まだ意味のある部分（解析結果の食い違いの検出・注意書き・ボタンの無効化・検出画像の写真の抑止）を残し、「復元の再生」に当たる部分は、**要らなくなった**として書いた（開き直しても、回答が届いたときと同じく、何も開かず・替えない）。ユーザー決定 U5（「古い会話を開いたら、結果領域は復元せず、注意書きを出し、そのカードのボタンを無効にする」）は、そのまま守っている。

下書き v2 の規則（参考。画面が変わる前の前提。採るなら、いまの画面に合わせて読み替える）:

0. 開き直しの始めに、結果領域を「新しい会話」と同じ最初の状態へ戻す。
1. 開き直した会話の回答を、**古い順に全部**、回答が届いたときと同じ処理（地図の表示 `focusMap` → `answered`。`viewForResults`・`filterFromResults`・`map_focus` の寄せ・`detection_image` の選択）へ通す。最後まで通すと、その会話を最後まで画面で見たときの状態になる。
2. **静かに通す（3 つ目の経路 `restoreView`）:** `switchView` は結果領域を開き、読み上げを出し、縦に積む幅でスクロールする。`chooseView` は結果領域を開かない。復元は、結果領域を開くが、読み上げ・スクロール・フォーカスの移動はしない経路にする。
3. 地区の一覧・候補の地図データ・`GET /api/health` の読み込みが終わってから、1 回だけ行う。
4. run が変わっていたら、その回答は通さない（`run_id`・`run_created_at` の比較。spec-prototype §7.1.5 に残した）。
5. run が違う回答があるときは、注意書きを出し、そのカードのボタンを押せなくする（spec-prototype §7.1.5 に残した）。
6. 結果領域へ効く回答が 1 件も無い会話は、既定のまま（結果領域は閉じたまま）。

あわせて、下書き v2 の「採るときに直す既存の記述・コード」の表にあった spec-prototype §7 の直し（「画面を自動で切り替えるのは、チャットの回答が来たときだけ」に、静かな復元を足す）は、その文がいまの §7 に無い（画面の変更で消えた）ので、反映しなかった。下書き v2 の未確認「spec-prototype §7 は結果領域を開く回答に『表・一覧』を挙げるが、`viewForResults` は…」も、前提ごと消えたので、載せない。

## 選ばなかった案

**保存の方式（D1）:**

| 案 | 内容 | 採否と理由 |
|---|---|---|
| A. 回答と一緒にサーバーが保存（採用） | `POST /api/chat` が `conversation_id` つきのときだけ保存する | 保存する回答の `results` を、サーバーが作った値だけにできる。回答と保存が 1 回の呼び出しで、食い違いが作られない。DocuNavi と同じ |
| B. 画面が、回答のあとに別の API で保存 | `POST /api/conversations/{id}/messages` に、画面が発言と回答を送る | 不採用。画面が送る `results` を、サーバーが信じて保存することになり、作り物の件数・座標を履歴に入れられる。回答の表示と保存が別の通信で、片方だけ失敗しうる。既存の `POST /api/chat` の契約を変えずに済む利点は、A でも `conversation_id` を任意にして保てる |
| C. DocuNavi そのまま（画面は最後の発言だけを送り、サーバーが履歴から文脈を作る） | 要求の `messages` を無くす | 不採用。未ログインの契約が変わり、Go への置き換え（ADR 0005）の途中で契約を動かすことになる |
| D. 保存に失敗しても回答は返し、画面が「保存できませんでした」と出す | 失敗を画面に知らせるだけ | 不採用（ユーザー決定: DocuNavi と同じ）。回答が見えて履歴に無い食い違いが作られる |

**そのほか:**

- **JWT をサーバー側で付ける**（JobNavi の `userToken()`。履歴の通信だけ Next.js の Route Handler を通し、`proxy.ts` の転送から外す）: ブラウザーは JWT を見ない。不採用の理由: Route Handler と転送の除外が増える。`/api/auth/token` は、jwt プラグインを設定したいまの web がすでに公開しているので、JavaScript から JWT を読める危険は、新しく増えない。
- **Python の API に先に入れて、あとで Go に移す**: 二重実装になるので勧めない（ユーザーが決める）。
- **サーバーが `conversation_id` を作って返す**（DocuNavi の方式）: 「`Authorization` を見ない」既存の契約と衝突する。
- **API の側で保存済みの件数と画面の件数を比べて、欠けた往復を見つける**: 画面の履歴は、失敗した発言・40 件の切り詰めで、保存済みの件数とずれる。
- **NUL を取り除いて保存する**: 保存する値を作り替えない。`conversation_id` つきは 422 にする。
- **一覧のページ分け・冪等キー・LLM による題名づくり・共有・検索・ピン留めなど**: DocuNavi に無いので足さない（spec-prototype §2.3.1）。
- **保守コマンドを Python にする**: 履歴の表の定義・削除の規則が 2 つの言語に分かれる（ADR 0005）。
- **保存を 50 件に収めず、保存期間だけで消す**: 一覧に出ない会話を、本人が消せないまま溜める。

- **LLM の出力の NUL:** 実 LLM（Gemini）が NUL を含む文字列（`content`・`tool_calls` の引数・`refuse` の `message`）を返すと、保存が失敗する（500）。模擬モデルは、NUL を入力の段で断るので起きない。実 LLM の出力から NUL を取り除く規則（`conversation_id` の有無に関わらず、`message` が変わらないように、Go のチャットの実装で、検査の前に行う）は、Go のチャットの段が終わってから決める。
- **実データでの 1 会話の大きさ**（`results` の jsonb の合計）。実データの熊本 12 タイルでの実測はしていない。バイト数の上限は、実測のあとに決める。
- **後処理の `--created` で同じ時刻を明示して入れ直す**と、`run_id` も `run_created_at` も同じで、別の解析結果と見分けられない。通常（`created` の既定は現在時刻）は起きない。内容のハッシュを `runs` に持たせる案は、`runs` の表を変えるので、必要になってから決める。
- **画面に、件数の上限（50 件）と自動で消えることを知らせる表示が無い**（初版。404 の文でだけ伝わる）。
- **開き直しの読み上げ・狭い幅・テーマ・キーボード操作**は、実画面で確かめていない。**`GET /api/health` の読み込みが終わるまでの、回答のカードの扱い**（spec-prototype §7.1.5 の規則 2）も、実装のときに決める。
- **公開（P7）の前に決めること:** 掃除の定期実行の仕組み、1 日あたりの書き込み数の上限（DocuNavi にも無い）。
- **ストリーミング（ADR 0005 の「その後」）を足すとき:** 保存は回答が完成した時点で 1 回行う。切断したときは保存しない（案）。DocuNavi の切断時の保存の扱いは確かめていない。
- **Postgres の消した行の領域・DB のバックアップ:** 消した行は、autovacuum が回収するまでディスクに残りうる（一般知識）。DB のバックアップ・ダンプからは消えない。TownScan に DB のバックアップの手順は見当たらない（`git grep`。CLAUDE.md の `backups/` の中身は読んでいない）。バックアップを作るようになったら、保存期間と合わせて決める。
- **一般知識で確かめていないもの:** NUL が `text` で SQLSTATE 22021、`jsonb` で 22P05 になること（この環境で DB を触って確かめていない）。H-C5（250 往復）の実行時間（数秒の見込みで、実測はしていない）。空白の集合の数え方（Python 29 個・Go 25 個）は、起草時の確認で、この変更では再確認していない。
